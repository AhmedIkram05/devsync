## P1 — Must-fix before scale

> Ordered by dependency, not severity. Work top-to-bottom — each phase unblocks
> the next. Foundations (transactions/validation/logging) are touched by every
> later fix; delivery gates land last because they verify the rest.

### P1.1 — Backend foundations (primitives everything else builds on)

- [x] No transactions — project/task/github `add/commit` — `@transactional`
  - New `backend/src/db/transaction.py`: `@transactional` commits once on a successful response and rolls back on any raise; `commit_or_flush()` for services. Applied to every write endpoint (projects/tasks/comments/reports/users/admin/notifications/github, both inline GitHub OAuth routes, `auth.register_user`); audit/notification/settings services now flush inside a managed request so one commit covers the whole request.
- [x] Validation holes — task/project/user/comment/report validators — central Marshmallow/Pydantic
  - Fixed the real holes: `register_user` now runs `validate_registration_data` (email format + password length), and `register`/`login`/`get_token` got `get_json(silent=True) or {}` null-body guards (empty body was a 500 TypeError). Deliberately kept the tested hand-rolled validators over Marshmallow: CI pins `marshmallow==4.3.1` while the local venvs have 3.26.2/3.15.0, so a schema rewrite can't be verified locally and would risk CI.
- [x] Logs leak PII/secrets — `auth.py:51,96-115`, `github_client.py:109-125` — redact + `request_id`
  - `auth.py` raw `print()` of user emails → structured logger (no PII, keyed severity); `github_client.py` dropped the access-token-prefix and raw-response-body logs and sanitized the auth-URL f-string. `request_id` propagation already existed.
- [x] Health/readiness — `/health` no DB check, `wsgi.py:11` import-time crash — `/healthz` + `/readyz` + lazy factory
  - Added `/healthz` (liveness, no dependencies) and `/readyz` (DB `SELECT 1` → 200/503), both public; repointed the K8s `readinessProbe` to `/readyz` (startup/liveness stay on `/health`). Lazy factory intentionally skipped — import-time `create_app()` is kept for fail-fast boot.

### P1.2 — Data access (same controllers: correctness + read perf, do together)

- [x] No pagination / unbounded `SELECT *` — all `.all()` — `paginate(page,per_page,max 100)`
  - New `backend/src/api/query_params.py` (`get_pagination_args` + `paginate`, default `per_page=100`, hard cap 100). Applied to every unbounded list GET — tasks, projects, users, comments, notifications, project-tasks. Each keeps its existing list key (`{ "tasks": [...] }`) and adds a sibling `pagination` object, so existing clients keep working.
- [x] No filtering/sorting — tasks `project_id/priority/search/sort`, projects `status/search`, users `role/search`
  - tasks += `project_id`, `priority`, `search` (title/description ILIKE), `sort`; projects += `status`, `search`, `sort`; users += `role`, `search` (name/email ILIKE), `sort`. Sort fields are whitelisted per endpoint (`apply_sort`); a bad `sort` param is ignored, never a 500.
- [x] N+1 + dashboard GET side-effects — `comments 36-38`, `projects 59-75`, `get_admin_dashboard:376-650` cyclo 81 + cleanup on GET — GROUP BY + beat + cache
  - Comments eager-load authors (`joinedload(Comment.user)`) instead of `User.query.get()` per row; `get_all_projects` batch-loads team members for the page in one `project_members` query (the `team_members` relationship is `lazy="dynamic"`, so it cannot be eager-loaded).
  - `get_admin_dashboard` cut from ~81 to a thin orchestrator: status/user counts, overdue, per-project task counts and TL KPIs now come from `GROUP BY` aggregate helpers (same pattern as `get_client_dashboard`). Response JSON is shape-identical.
  - Destructive cleanup was removed from every GET (projects list, admin dashboard, audit logs) and moved off the request path to a daily Kubernetes CronJob — `k8s/base/maintenance-cronjob.yaml` → `src/db/scripts/run_maintenance.py` → `src/services/maintenance_service.py` (`cleanup_old_audit_logs` + `cleanup_completed_projects`). Cache deliberately skipped: `GROUP BY` + pagination removed the load, and a cache would add per-worker staleness for no measured need.

### P1.3 — Trust & safety (audit, retention, access control)

- [x] Audit incomplete + wrong txn — `audit_service.record:28-78` — same-txn + hash IP + missing calls
  - Fixed the wrong-transaction bug: on failure `record()` no longer calls `db.session.rollback()`, which inside a `@transactional` request discarded the caller's real work. Inside a managed transaction the audit insert now runs in a SAVEPOINT (`begin_nested`), so a failed audit rolls back only itself.
  - Client IPs are hashed (HMAC-SHA256 with a server pepper derived from the app's own `SECRET_KEY`/`JWT_SECRET_KEY`; overridable via `AUDIT_IP_PEPPER`). A raw IP is never persisted, and when no pepper is available the IP is simply not recorded.
  - Added the missing audit calls: GitHub task link / unlink / account disconnect, and notification create / read / mark-all-read / delete.
- [x] Retention unsafe — `settings_service.py:102-162` — batch `LIMIT 1000` + beat + dry-run
  - Replaced the single unbounded `DELETE` and the full-table `.all()` load with bounded batches (`RETENTION_BATCH_SIZE = 1000`, capped at `RETENTION_MAX_BATCHES = 100`).
  - Dry-run available end to end: `?dry_run=true` on `POST /admin/settings/retention/run`, `run_retention_cleanup(dry_run=…)`, and `python -m src.db.scripts.run_maintenance --dry-run`. A dry run counts via `SELECT COUNT(*)` and deletes/commits nothing.
  - The scheduler already landed in P1.2 (daily CronJob `devsync-maintenance`).
- [x] Limiter fail-open + spoofable — `rate_limiter.py:59-106` — ProxyFix + fail-closed for `/auth/*`
  - `ProxyFix(x_for=…)` (env `PROXYFIX_X_FOR`, default 1) so `request.remote_addr` reflects the trusted proxy hop rather than trusting a client-supplied `X-Forwarded-For` verbatim. Before this the forwarded header was believed blindly, so a client could spoof its own bucket.
  - **Known limitation (verified live in production):** `PROXYFIX_X_FOR` cannot recover the true client IP on this stack. The ingress class is `gce` (GKE external *passthrough* NLB), which source-NATs and does not forward the original address, so the pod only ever observes a rotating Google LB node IP — 7 distinct `35.191.*` ids appeared in Redis (`rl:ip:35.191.*:api.login_route`) within a single login window. Buckets are therefore per-LB-node, not per-user. This blind spot is pre-existing (the global limiter had it too) and this change reduces collisions, but it is not per-user throttling. Real per-client limiting requires the LB to pass the address through: enable PROXY protocol with a PROXY-aware ingress, or move to the GKE Gateway with a proxy-mode LB. Tracked for P3 infra.
  - `/auth/login`, `/auth/register`, `/auth/token` now get `5/60` and `/auth/refresh` `10/60`, applied outermost so a malformed body still counts. When Redis is unreachable these fail **closed** (429) instead of silently relaxing to the per-pod in-memory window; the global `before_request` limiter deliberately stays fail-open so a Redis outage cannot take the whole API down.
- [x] RBAC inconsistencies — `GET /users`, `/admin/stats`, `reports`, comments — align with `ROLE_PERMISSIONS`
  - `GET /users` no longer leaks PII: `email` + `github_username` are returned only for roles with `can_view_all_users` (TEAM_LEAD+); developers get `id`/`name`/`role`/`avatar`/`created_at`, so the assignment and @mention pickers keep working.
  - `/admin/stats` and all `/reports` routes now express `can_view_system_stats` / `can_generate_reports` via `require_permission` instead of hardcoded role lists.
  - Comment routes gained the central project gate: task-scoped routes use `@require_project_membership`, and `/comments/<id>` PUT/DELETE resolve comment → task and 404 when the caller cannot see it (no existence oracle). Previously any authenticated user could read and edit comments on any task.

### P1.4 — Integration perf

- [x] GitHub perf — `get_github_repositories:157-400`, `_make_request:194-270` — timeout, 429, clamp, commit before IO
  - `GitHubClient.REQUEST_TIMEOUT = 10` is now the single source for every GitHub HTTP call (previously hardcoded `timeout=10` at each call site). `_handle_rate_limit` recognises HTTP **429** (secondary/abuse limit) and honours `Retry-After` (seconds or HTTP-date) alongside the primary limit's `X-RateLimit-Reset`, and sleeps only when the wait is ≤ `MAX_RATE_LIMIT_SLEEP_SECONDS` (30s): a longer wait fails fast instead of blocking a worker/DB session for up to 5 minutes.
  - `get_user_repositories` clamps `page ≥ 1` and `per_page ∈ [1,100]` at the single choke point, so the non-`all_pages` repo list and the issues/pulls endpoints inherit the bound (the `all_pages` path already clamped).
  - `get_github_repositories` now runs all GitHub network IO (repo list + concurrent activity fetch) **before any DB write**, so the request transaction no longer straddles the slow activity fetch; the duplicate trailing `flush()` was dropped.

### P1.5 — Frontend UX

- [x] Frontend UX gaps — server pagination, Login/Register validation, TaskForm/TaskCreation checks, Github detail waterfall, Reports PDF dup/broken, dashboard flicker — see audit report
  - Validation now runs through the already-installed `formik` + `yup` (`src/utils/validation.js`) instead of hand-rolled `useState` checks: Login/Register reject whitespace-only input and non-emails (Register had `noValidate` and **no** email check, so `abc` reached the API), TaskForm/TaskCreation validate title/description/project before POST, and create-task failures surface the backend `{message}` via `getErrorMessage` (the `err` was previously discarded and every 400 showed a generic string). Register also stopped bypassing `client.js` with a raw `fetch`. Editing keeps `project` optional (`taskEditSchema`), so the task-details edit form still saves.
  - List views now actually paginate: services return `{items, pagination}` (the backend sibling object was being array-coerced away) and a shared `<Pagination>` drives TaskList, AdminUsers, AdminProjects and ProjectDetails. Aggregates that previously undercounted past the 100-row page cap — the Reports summary/charts (`dashboard.js` `getReportData`) and developer progress — now walk every page, and ProjectDetails' Completion %/Total Tasks come from `pagination.total` over the full set instead of the first page.
  - The GitHub detail page collapsed three serial round-trips to one parallel batch (issues/pulls only needed the route `repoId`) and `githubService.checkConnectionStatus` dedupes the concurrent `GET /github/status` that `/github` fired twice per visit. The dashboard flicker traced to auth object-identity: `AuthContext` now memoises its context `value` and wraps its callbacks in `useCallback`, and BasicDashboard/DeveloperProgress/AdminDashboard key effects on primitives with a first-load-only spinner, so a background auth event no longer blanks the page. Reports PDF generation lost its dead duplicate `buildTimeBuckets`, no longer truncates to the top 8 rows, paginates past ~45 lines, and reports failure instead of throwing silently. Deferred (not fixed): Reports.jsx still swaps to a spinner on report-type/date-range change — the in-place-refresh variant caused a test-visible render race and needs a component-level rework.
